# Mux Bot: agent instructions

Mux Bot is the friendly, free, open-source app for darkmux (iOS and macOS, one SwiftUI multiplatform target).

## Build

The Xcode project is generated and gitignored. Never edit or commit `MuxBot.xcodeproj`; change `project.yml`.

```bash
xcodegen generate
xcodebuild -project MuxBot.xcodeproj -scheme MuxBot -destination 'generic/platform=iOS Simulator' build
xcodebuild -project MuxBot.xcodeproj -scheme MuxBot -destination 'platform=macOS' build
```

Both builds must pass before a push. Signing: `DEVELOPMENT_TEAM` is never committed (forks are encouraged). Copy `Config/Local.xcconfig.example` to `Config/Local.xcconfig` (gitignored), or set the team in Xcode.

## Design philosophy

Mux Bot is about getting work done, not managing machines. Lead with the work (runs, results, what needs you); machines, models and config appear only as details of a run or in conversation with a bot. Only bots act, always behind an Approve card; other screens are read-only. Bots are projects or themes the user names; darkmux roles are the crew underneath. Status is shown with icons and motion, not words (`StatusBadge`; words only in accessibility labels).

Use Apple's built-in frameworks wherever they fit, before writing custom code: CloudKit for sync, Keychain (and Secure Enclave / CryptoKit for pairing keys), Foundation Models, App Intents, WidgetKit and ActivityKit, UserNotifications, LocalAuthentication, Handoff, Speech.

## Rules

- **No third-party dependencies.** Apple frameworks only, and prefer a system framework over custom code (see the design philosophy).
- **Swift 6, strict concurrency complete.** UI state types are `@MainActor @Observable`.
- **Only bots act, and only after Approve** (one exception: a setting's switch in a guide card, which you flip yourself). Work starts in conversation: the one chat bar (`BotBar`) follows navigation and talks to the bot on screen (the lead bot, `LeadBot`, on Home). Dispatches to the crew are run cards; handoffs, new bots and new resources are action cards (`MessageKind.actionCard`, `ActionCardView`, decided once by `BotBrain.resolve`). All are saved in the thread, so several can wait at once and they survive a relaunch. The Activity tab is read-only: a row opens its run's card in the bot's thread.
- **The run loop is human-in-the-loop, as thread cards** (`MessageKind`, `RunCardView`): a dispatch card (Approve / Cancel) → a live run card → the result as the bot's reply. darkmux commits every finished run that changed files to the bot's branch (a checkpoint), so the reply has one **Undo** (darkmux reverts that run's commit; refused while a later run changed the same files) and the hint "Reply to change it": your next message in the thread continues the same run (a Tweak, sent with `continues`). A run that changed nothing shows its question with tap-to-answer buttons. After an Undo the card collapses to "Undone". Opening a PR is a later step (after GitHub sign-in, a design decision since darkmux retired PR authoring). Only approvals and questions need you (`BotRun.needsYou`): they're the badge, Activity's Needs you, and the thread's pinned banner. The banner's × hides those items on this Mac everywhere (sidebar badge, Activity, menu bar and Dock counts) until something new needs you (`NeedsYou`, ids kept in `LocalBotState`); the run and the synced `Bot.state` are untouched. Internal names stay (`RunPhase`, `.keep`/`.discard` events, darkmux's keep/discard routes for older clients). Transitions live in one state machine (`RunPhase.next(on:)`, applied by `BotStore.apply`). A run says what really happened: "Stopped." only when darkmux says `cancelled` (your Stop, accepted by darkmux); an error is a failure worded from darkmux's `code` (`RunResultText.failure`), and a run darkmux forgot (404) fails with `RunResultText.lostTrack`. Only runs this device started (`BotRun.startedHere`, run ids in `LocalBotState.localRuns`, never the synced store) are followed, stopped, undone or block a new run here; another Mac's runs say "Stop it from the Mac it runs on." A run approved just before the app quit (no work id) fails on relaunch (`quitBeforeStart`). A 401 means darkmux forgot this app: it unpairs with a plain sentence and shows pairing (`FleetConnection.revoked`). Deleting a bot cancels its runs and preview first (`RunCoordinator.prepareToDelete`); Clear Conversation keeps open runs' latest cards; a hand-off is a dispatch card in the other bot's thread. A Tweak never costs the result it continues: if it can't start, fails or is stopped, the run goes back to that result (its summary, Undo and Open PR) with a line saying why (`RunCoordinator.restoreTweak`). The result before it is kept on this Mac (`LocalBotState.tweakBases`, so a relaunch keeps it too), and until darkmux accepts the Tweak the run has no work id (the earlier turn's is never followed or stopped as the Tweak's): a Tweak still waiting for a slot is stopped here at once, and one darkmux never had goes back to its result on relaunch; darkmux refusing to continue (409/404) sends the change as a fresh run. Each turn is its own darkmux commit: a run keeps every work id (`LocalBotState.runWorkIds`), Undo reverts them newest first (stopping, and saying so, if darkmux refuses one), and the card shows the union of changed files. darkmux at its limit of two runs for this app (429) leaves the card approved and "Waiting for a free slot" until one ends (`slotFreed`). Only crews that change files are auto-tweaked by your next message; a review or research result gets Done. A stopped or failed run is offered as a follow-up once. Corrections ("no, it's a question") match whole words and stop a Tweak the misread started. "Thinking" and the keyword-fallback note are per thread. Nothing is ever simulated: a run that can't go to darkmux doesn't start, and a refused submit fails the run (`.fail`).
- **Live preview** (`PreviewPanel`, SwiftUI `WebView`): Full window (`AppRouter.previewFullScreen`) ends when you hide the preview, leave the bot, or a reply or card arrives in its thread (`attentionArrived`), so it never outlives its bot or hides what needs you. Leaving a bot's thread stops its preview after a 30-second grace (`RunCoordinator.leavePreview`, `previewStopGrace`); coming back within it (`enterThread`, or SwiftUI rebuilding the view) calls the stop off, a start while its thread is off screen (a refresh after a run, the connection arriving) stops after the grace too, so darkmux never gets a stop and then a new start; the Stop button and quitting stop at once. Each bot's preview gets its own fresh page (`PreviewController.show(_:for:)`), and back/forward is refused (`PreviewNavigationDecider`, gestures off, Delete outside a field swallowed by the page script), so no key or swipe ever shows another bot's page or a stopped preview's cached one. A link to another site opens in the browser; the header shows the page's own host, and Reload (`PreviewController.goHome`) loads the preview's page again. Pick mode survives loads (its script is put back after each one) and the chip starts it once the bot's page is there. A pick belongs to its bot (`PreviewController.pickedBot`, `pick(for:)`): its chip shows and is sent only in that bot's thread. A stopped preview's page is let go (`onPreviewStopped`, `forget`), so nothing measures it. The page remembers the `previewReloads` count it was loaded at, so a run that changed files while the panel was closed reloads it on reopen; a status hiccup after a run reloads, never restarts. iPhone and iPad's full-screen preview records its bot (`showFullScreen`) and has Reload. A cached "ready" is checked with darkmux before it's trusted (stale or 404: started again); a status poll tolerates a hiccup; the heartbeat beats first, and three misses say darkmux isn't answering (`Unavailable.notAnswering`, with the start command). A stop is always sent when this app asked for the preview. Preview refusals branch on darkmux's `code` (`template_no_recipe`, `no_source_checkout`, `no_recipe`), and failures on its own reasons (Docker, container, loopback-only, not answering, "install (…) exited"). The done-when check uses darkmux's preview of the work copy as it is now (never a preview link of yours) and, if none is running, says so with Check again and runs once it's ready. a bot thread shows a Preview toggle when the bot has a preview URL; split beside the chat on macOS, a full-screen cover on iPhone and iPad (`PhonePreviewScreen`); a run card's "Live" opens it. The bot info sheet checks each repo for `.darkmux/preview.json` (from the bot's workspace through darkmux, else read-only from GitHub). darkmux runs a bot's preview in its work copy from the repo's `.darkmux/preview.json` (`command`, `env` with `{port}`/`{hmrPort}`, `ready`, `install`, `env_from_source`) on its own free ports, and the app shows its URL once ready (`LivePreview`, `RunCoordinator.ensurePreview`; the panel shows `PreviewStatusView` while it starts or if it failed). A failure is a plain sentence about what happened and what to do (`PreviewFailure`, mapped from darkmux's reason and the server's output: Node too old, install failed, port in use, preview settings, too slow, server stopped, else general); the raw output is only behind a closed "Show details" with Copy (`TechnicalDetails`). **Start over** (`RunCoordinator.startOver`) asks darkmux for a clean restart (`{"clean": true}`, darkmux #3484): it reinstalls the project's packages and starts the preview again, offered next to Try again (leading for install problems, `PreviewFailure.startOverFirst`) and in the panel's size menu while it runs. It shows only where darkmux supports it (`DarkmuxClient.supportsCleanStart`: an unknown body key on a made-up workspace is a 400 there and a 404 on an older darkmux; nothing starts), never as a plain restart that looks like it worked. The same goes for GitHub sign-in (`GitHubAuth.SignInRefusal`, `failureDetails`), work copy setup and every other failure: never paths, stack traces, status codes or env var names up front. darkmux's errors are worded by status and `code` (`DarkmuxPlain`, `RunResultText.failure`, `undoRefusal`) and GitHub's by status (`GitHubPlain`), with the raw text behind Show details (`workCopyDetails`, `decisionDetails`, a failed run's details); the thread names the crew (Reviewer, Researcher), never darkmux's role. Without a work copy, a preview link you add is shown instead (never commit a tailnet hostname). ATS allows plain http for `*.ts.net` only, until tailnet HTTPS certificates are on.
- **Work copies belong to darkmux.** A bot keeps its GitHub repo, and on this Mac a darkmux workspace name (`Bot.workspaceName`), never a path. Add folder (Open panel, security-scoped bookmark, `GitRemote` reads the repo from its git config) has darkmux make a worktree of your checkout on its own `mux/<bot>-<id>` branch from the fetched default branch, so your working tree is never touched; with no folder, darkmux clones the repo. A dispatch card for a bot with code but no workspace asks "Set up … on this Mac?" first (`RunBlocker`).
- **The app picks the model per run** (`ModelChoice.resolve`, `RunCoordinator.runProfiles`/`runChoices`, in memory on this Mac). darkmux lists the profiles this app may use here and which answer now (`GET /client/profiles`: the role's own first, then every other local one). Settings › Models sets the mode per darkmux machine (its models differ) and the Auto order, shared as names; a bot can override the mode per machine. They're about target machines, not this device, so they live in `ModelSettingsStore`: iCloud key-value storage when sync is on (`MUXBOT_CLOUD_SYNC`, the `ubiquity-kvstore-identifier` entitlement), this device's defaults otherwise; never `LocalBotState` or SwiftData. A machine is keyed by the stable id darkmux reports (`RunCoordinator.machine`, from `GET /client/profiles`), remembered with the settings so it's known after a relaunch and on iPhone (`ModelSettingsStore.lastMachine`, `RunCoordinator.knownMachine`); until darkmux has named it once, model settings aren't shown or saved, and iPhone says "your Mac (name)". Each crew's models come from its own role (`?role=`, `listedByRole`). A card with no model choice (proposed on another device, before a relaunch, or Approve before the listing came back) chooses on screen ("Choosing the model…"), and Always ask or a missing default model is shown, never skipped: **Auto** (default) takes the first in the Auto order that's running, and "Run again with these numbers" after a done-when that wasn't met takes the next; **Always ask** shows a picker on the dispatch card with Auto's pick preselected and its reason; **a default model** runs every time, stays on it after a done-when not met and offers the next one, and when it isn't running or listed the card says so and offers Auto's pick (never swapped silently). No name in the order listed: darkmux's default for the role, never some other local model; nothing listed (an older darkmux): darkmux's own default. Models stay out of card headers: only the Always ask picker row, "What Coder gets" (with a one-run Change) and the run's Details.
- **Done-when, checked.** A dispatch whose brief came from a measurement (`LayoutMeasure`) keeps a check (`LayoutCheck.Spec`, in `RunCoordinator.checkSpecs`, in memory on this Mac): after the run, if it changed files, the app measures the preview again and the result card says "Done when: met" or "not met" with what failed, and offers "Run again with these numbers". Never judged by a model.
- **Bots can't see; they measure.** A described visual problem is a bug report, never judged by the model: `BugReport` runs `factsScript` in the preview (`PreviewController`, `PageInspecting`) to measure the matching element, then posts a bug card (`BugCardView`): one plain sentence (`BugDraft.headline`, from `LayoutMeasure.Measured.plain`), the measurements behind a closed Show details (`TechnicalDetails`; the issue and Coder's brief carry them all), "File on GitHub" (prefilled issue URL, preview screenshot on the clipboard) or "Fix it now" (a Coder dispatch card, made once: the bug's message keeps its run id, and the button becomes "Sent to Coder" until that run is canceled or fails before darkmux had it, `BotStore.sentRun`). A bug measures and screenshots only its own bot's preview (`facts(for:bot:)`, `snapshotPNG(bot:)`), and keeps the crop it was sent with (`BugCrops`, by message id, on this device); File on GitHub copies only that. A complaint about the page itself running off the side ("off the screen", "scrolls sideways", "wider than"; `BugReport.isPageOverflowComplaint`), with nothing picked, when the page fits at every width measured is no bug (anything else, a picked element or "cut off", is measured into a bug card): the bot says so plainly (`BugReport.pageFitsText`, a `GuideCard.pageFits` with Reload the preview), since the preview panel may be what's clipped. The panel's device frame always fits the panel's current size (`PreviewViewport.shown`).
- **Point, don't describe.** In the preview, Pick (hover, click) or select text → **Chat about this** (the one action) attaches the element (`PickedElement`: selector, measurements, the selected text, cropped snapshot) as a chip in the bar for one message, and the preview keeps it outlined (and a text pick keeps its selection) while the chip is attached: `__muxMark`, redrawn after a reload or re-render, hidden when the element is gone, removed with the chip (`PreviewController.clearPick`), and what you type decides what happens (`Intent.infer` with an element, or a prefix): a change ("make this bigger", "replace this with…") is a Coder dispatch card naming the element and the selected text, a remark or a question naming a problem ("why is this cut off") is measured into a bug card, and any other question is answered (`BugReport.pageScript`, installed on every load, and `pickerScript` post picks to the app through a WebKit message handler; `PreviewController`, `PickRelay`).
- **Intents:** inferred by default (`Intent.infer`), or set with a prefix (`bug:`, `fix:`, `review:`, `ask:`, `issues:`). A correction like "no, it's a question" re-answers your previous message under that intent (`Intent.correction`). `ask` never proposes work.
- **Repo hints come from the repo.** A run's brief adds the repo's own `conventions` and `page_file`; the app never guesses a framework's layout. Since template schema 2 they live in the playbook (`page_file`, `pages`, `viewports` header keys and `## Conventions`; `Playbook.hints`, `RepoHints`): the template's for a bot made from one, else the repo's own PLAYBOOK.md (`RecipeStore.hints`), merged into darkmux's recipe (`PreviewManifest.with`). `.darkmux/preview.json` is darkmux's own recipe (`schema_version` "1.0", darkmux's keys only, `HOST` 0.0.0.0 since darkmux runs previews in a container); schema 1 files with the hints in preview.json still read.
- **Mux Bot, the lead bot, is a guide** (`MuxBot/Features/Guide`, behind `Guide.isEnabled` and one call in `BotBrain.respond`, so it can be cut). In its thread it answers five things (`GuideRoute`) and never starts work or improvises (a message no route, hand-off, new-bot or work-status path takes gets `LeadGuide.menuText`, what he can do): **start a project** (`.startProject`: "new project", "write a book", or a template's name opens Start, straight to the form of a template the registry names by id or title word, never a hard-coded list; a question about it goes to help); a **setup check** (`SetupCheck`, a live checklist card that re-checks what answers on this Mac every few seconds: Apple silicon, darkmux's app connection on 8767, LM Studio on 1234, Docker (you confirm it; the app can't see it), pairing, darkmux's model listing, GitHub; each step has a plain-words line, a Copy command and a link, since the sandboxed app can't run commands, and one block at the top installs everything still missing with a rough time and download estimate (`SetupCheck.setupBlock`); on iPhone it says runs need a Mac and shares the steps); a **first bot** from a pasted repo link or folder (an Approve card, `BotDraft.resource`) or New bot; **help** from the bundled articles (`Guide/Help/*.md`, `HelpLibrary`: on-device retrieval where word coverage decides what's known, threshold 0.5, and NaturalLanguage sentence vectors only rank; the on-device model answers from the matched parts, else the article's own words; every answer cites its article, and below the threshold it says it doesn't know); and **settings** (`GuideSettings`): it explains a setting and posts a card with the real control bound to the live value. Flipping that switch is the approval and applies at once (app settings only). darkmux's settings show their value read-only, only once paired, and say they're changed on the Mac. Guide cards are `MessageKind.guideCard` with the `GuideCard` JSON in `actionJSON`. Help articles state only what the app and darkmux do today; update them with the feature they describe.
- **Use cases are templates with a playbook** (`MuxBot/Features/Start`). "Start a project" ("What do you want to get done?", shown even with one choice) lists the template registry: `templates.json` in kstrat2001/muxbot-templates, read unauthenticated from GitHub, cached, with a copy built into the app (`Start/Templates`); entries are `owner/name` repos pinned to a full commit SHA, never a branch or tag (`TemplateRegistry`). A template missing at its pin says so; offline, the built-in copy is used only when it's of the same pin, and a template that couldn't be read is tried again when Start appears. Each template carries a root `PLAYBOOK.md` (`Playbook`, parsed by hand: a `key: value` header, then `## Questions`, `## Persona`, `## Skill: <name>` sections, and an optional `## First run`) and `.darkmux/preview.json`. templates.json and PLAYBOOK.md follow one versioned schema (kstrat2001/muxbot-templates SCHEMA.md, `TemplateSchema`, now 2; schema 1 still reads), and a schema 2 template's `.darkmux/preview.json` is darkmux's own recipe: a missing schema, a newer one ("this template needs a newer Mux Bot"), a missing required key or section, or an unknown key is refused by name, never guessed; the picker shows why. A template is used only at its pinned commit (its install runs on this Mac; its playbook is model-facing). Starting one (`StartProject`) reads only the entry and its playbook, never use-case code: a bot from the persona with a fresh look (`BotLook.fresh`: a random animal among the least-used, never the lead bot's octopus, in a body color no bot of that animal has yet; made when you pick the template, with Shuffle on the form; the playbook's `animal`/`colors` are still read but don't set it), its use case (`Bot.useCaseId`) and the playbook's skills copied in (`Bot.skillsJSON`, so a later template never changes it), the bot greets you in its own words (`BotGreeting`, never the persona) and, when the playbook has `## First run`, posts a dispatch card built from your answers (`Playbook.firstRunTask`: `{name}`, `{purpose}`, `{feel}`; a line whose answer is blank is left out), so the first tap is Approve; then darkmux makes a fresh local project from the template (`template: true` on workspace create: no history, no remote, named for the bot, never reused) and the preview starts. **"Back up to GitHub" is on by default**: the new project gets its own GitHub repo first (`GitHubRepoMaker`, sign-in required then): in your account, private unless you switch Public on, its name from the project's (the next free one when taken), created with GitHub's first commit (the Git Data API can't write to an empty repo) and then the template's files at the pinned commit as one commit on top (no fork, no link to the template); the template is read and checked before the repo is asked for (a submodule or a cut-short tree makes nothing), the description is the purpose on one line of at most 350 characters (`GitHubRepoMaker.describe`), a name GitHub says is taken moves to the next, and a refusal shows GitHub's own reason; only when that succeeds are the bot and darkmux's local project made, from the same commit. If it fails nothing is made here and the form says why, naming a repo that was made but couldn't be filled; a 403 means the GitHub App lacks the "Repository creation" permission. The bot keeps the repo, and on this Mac its start (`Bot.githubStart`: the GitHub start commit, default branch and `mux/<bot>`): darkmux's own first commit isn't on GitHub, so pushes build on the GitHub start. Every committed run is backed up to `mux/<bot>` (`RunCoordinator.backUp`, `GitHubPR.push`, no PR; the run's notification goes on its own so macOS's permission prompt never holds it up), and Open PR opens it into the default branch. Switched off, the project stays on this Mac with no sign-in, and "Put it on GitHub" in the bot's info does the same step later (`PutOnGitHub`): the repo from the template's pinned commit, then the project's committed work on top of its default branch, with later backups to `mux/<bot>`. The repo is recorded the moment it's made (`LocalBotState.putPending` until the work is in), so a failed push says so and "Finish putting it on GitHub" resumes into that repo, never a second one; backups wait for it. Then a new `mux/<bot>` goes on top of the pushed work (`GitHubPR.Start.parent`) while its tree stays based on the template's start (`Start.commit`, what darkmux's changes are against, so a file deleted after Put shows as deleted); the runs Put pushed aren't offered for a PR again (`LocalBotState.shippedThrough`, the time it read the changes), and one that finished meanwhile is backed up after. A repo Put made but couldn't fill is filled again by the next Put (`putMadeRepo`), never a second repo. The in-flight state lives in `RunCoordinator.puttingOnGitHub`, not the view. Per run, the skills that fit go into the brief (`BotSkill.relevant`, on-device retrieval). Bot info shows skills read-only. Each question is a full, never-truncated label above a left-aligned field (`QuestionField`; multi-line for sentences, one line for the name), and its trailing "(For example: a, b, or c.)" becomes tappable suggestions that wrap (`PlaybookQuestion`, `WrappingStack`); Start needs a name and what it's for. A template bot made while unpaired or on iPhone has no project on this Mac: its dispatch card says so and offers to make it from the same template (`RunBlocker.projectNotMade`), never "add a folder or repo", and never a clone of its own repo, even when it was backed up to GitHub: the project is made from the template at the commit its repo started from, and its GitHub start is found again from the repo's "Start from …" commit (`GitHubRepoMaker.findStart`), so backups go on; until that start is found (it needs your GitHub sign-in) the project isn't made here, and a template project is never pushed to its local branch name: backup and Open PR look for the start again, and Open PR says plainly when it can't. Signed out, a backup says once per bot that it didn't happen. Start a project is always one tap away: a "+" in the sidebar (Mac, iPad) and on Home (iPhone), File › New Project… ⌘N (New Bot… is ⇧⌘N), and Mux Bot's chips, which stay while you type in his thread. With no bots, Home (and the Mac window's empty selection) opens on the chooser inline (`AppRouter.openOnStart`), with New bot and the example bot in the More menu, and a successful pairing with no bots goes back to it (`continueAfterPairing`). **Work on a project I already have** (`ExistingProject`, `ExistingProjectView`) is built in, not fetched, and has no template: a folder on this Mac (Add folder's flow) or a repo from your GitHub (`GitHubAuth.myRepos`, every page up to a cap; sign-in inline), with your own checkout used when another bot already has one (`knownCheckout`, its bookmark stays in `LocalBotState`), a name suggested from the repo, and skills from the project's own PLAYBOOK.md (schema 1 or 2) or the general ones (`Start/Templates/existing.PLAYBOOK.md`); one that can't be used says why on the form and in the greeting (`ParseError.projectMessage`), and Start waits while the repo's is read. A repo link approved in Mux Bot's thread is set up the same way and opens the bot. When darkmux finds no recipe (`RunCoordinator.noRecipe`), the thread offers it once on an Approve card (`BotAction.setUpPreview`, `PreviewSetupCardView`): every value editable with where it was found. Adding a use case is a new template repo and a registry entry, no app code.
- **The lead bot's name is a placeholder** (`LeadBot.name`, currently "Mux Bot"); change it there only.
- **The app owns its bot store.** A bot (`Bot`) is a project or theme: a persona, a thread, resources (`BotResource`: repo, preview link, link, note; folders come only from Add folder) and runs (`BotRun`). darkmux roles are the crew (`CrewRole`: Coder, Reviewer, Eval runner, Researcher): never bots or tiles, only named on dispatch cards and run details. Everything is in SwiftData, mutated through `BotStore`, not mirrored from darkmux config. Nothing is seeded: an empty Home offers one example bot on request (`BotStore.addExample`), so a second device syncing the same iCloud data never duplicates bots.
- **Versioned schema** (`MuxBot/Core/Models/Schema`): `SchemaV1` is the frozen pre-versioning store; `SchemaV2` is the live models; `MuxBotMigrationPlan` moves between them. Change a model only by adding a new version and stage, with a test that migrates a real on-disk store. A store that won't open shows `StoreRecoveryView` (Try again, or Start fresh, which renames the old files and never deletes them).
- **One thread per bot across devices:** a thread's id is its bot's (the lead bot's is fixed, `ChatConversation.threadId`), every lookup takes the oldest, and copies two devices each made merge into it, messages and all (`BotStore.conversation(for:)`, `mergeDuplicateThreads` at launch). A bot deleted elsewhere leaves its thread for Mux Bot's (`AppRouter.botsChanged`), with no chat bar under "Bot not found" and no new thread for its id.
- **Sync and machine-local data:** with `MUXBOT_CLOUD_SYNC = YES` and the iCloud entitlements (see `Config/Local.xcconfig.example`), bots, runs and threads sync through the user's private CloudKit database; models stay CloudKit-safe (no unique constraints, defaults or optionals, optional relationships; a test checks). What belongs to one machine (darkmux workspace name, picked folder bookmark) lives in `LocalBotState` (a file in the app's container, keyed by bot id), never in the synced store. The pairing token stays in this device's Keychain.
- **American English** in all copy, comments and docs.
- **GitHub:** "Sign in with GitHub" (`GitHubAuth`) uses the device flow with the Mux Bot GitHub App's public client ID (`MUXBOT_GITHUB_CLIENT_ID` in `Config/Base.xcconfig`; forks override it in `Local.xcconfig`). The token (and the refresh token GitHub gives with an expiring sign-in) stays in this device's Keychain. A 401 from GitHub, on a read or a write, renews the token once (`GitHubSession.renewed`, `GitHubAuth.renewal`, one shared renewal) and retries, and a kept sign-in is checked at launch; only GitHub refusing the refresh token signs you out with "Your GitHub sign-in expired. Sign in again." (`GitHubAuth.expiredMessage`), while a dropped connection or a GitHub hiccup keeps you signed in and says GitHub can't be reached. Signed in, GitHub reads carry it (private repos, 5,000 requests an hour). **Open PR** appears in a bot's thread when its branch has committed runs not yet in a PR: darkmux hands over the branch's committed changes (read-only `/client/workspaces/{name}/changes`), and the app creates the blobs, tree, commit, branch ref and PR through GitHub's Git Data API (`GitHubPR`). If the branch already exists on GitHub, the new commit goes on top of its head and the ref moves forward without force; if someone else pushed there, it never writes over their work: the bot's work goes to the next free name (`mux/<bot>-2`) from then on and the thread says so (`RunCoordinator.pushMovingOn`, kept in `githubStart` or `LocalBotState.pushHead`). A bot's pushes (backups and Open PR) run one at a time (`RunCoordinator.oneAtATime`). Never a force push; darkmux never authors PRs (darkmux #1463). If the App isn't installed on the repo, the thread says so with the install link; installed and still refused, it says that instead (`RunCoordinator.cantWriteText`), and a base commit GitHub doesn't have is its own message (`GitHubPR.Failure.baseMissing`). Tests mock every GitHub call (`GitHubStub`); there's no network in tests.
- **Network calls:** GitHub (`GitHubClient`, signed in or not; `GitHubAuth`; `GitHubPR`), and darkmux's local client endpoint on this Mac (`DarkmuxClient`, `127.0.0.1:8767`, prototype contract on a local darkmux build): pairing (`FleetConnection`, token in the Keychain), workspaces, runs, status, cancel and the preview recipe. The iPhone app can't reach it yet; it says runs start from the Mac app.
- **Bots answer on device** (`BotBrain`: Foundation Models guided generation with the `OpenIssuesTool` tool). The app can't see the darkmux fleet yet, and bots say so rather than guess. When the model is unavailable or fails (the simulator can report it available and still fail if the Mac has Apple Intelligence off), the thread says so once and `FallbackBrain` keyword matching answers: honest answers, never a fake "Noted".

## Layout

- `MuxBot/App`: entry point (on macOS one main `Window`, never a `WindowGroup`: a second window would share the router and the one preview page and follow every run twice; the menu bar item keeps the Dock badge so it counts while the window is closed), `ContentView` (macOS/iPad: `BotSidebar` of Mux Bot, bots, Activity, with the thread beside it; iPhone: Bots and Activity tabs), typed navigation (`AppRouter`, `Route`).
- `MuxBot/Core`: design system, the bot brain (`BotBrain` for conversation, `RunCoordinator` for runs, work copies and previews, `RecipeStore` for preview recipes, `FallbackBrain`, `LeadBot`), models (bots, threads, runs), services (`DarkmuxClient`, `FleetConnection`, `GitHubClient`, notifications), keychain, SwiftData container.
- `MuxBot/Features`: Home (Mux Bot featured as `LeadBotTile` + bot tiles; the sidebar features it too, `SidebarLayout`), Bots (`BotBar`, owned by the Bots tab and following `AppRouter.context`; `BotThreadView`; `BotInfoView` for resources; `NewBotView`), Activity (`ActivityView`, read-only runs in three groups: needs you, running, finished; a sortable table on macOS), Chat (transcript, run cards, action cards, bug cards).
- `MuxBotTests`: Swift Testing suites (`xcodebuild ... -destination 'platform=macOS' test`). They run inside the app (its test host, same bundle id and container), which then uses an in-memory store: tests must never open the real one. Defaults, the Keychain and `LocalBotState` are separate copies under tests (`TestIsolation`, `KeychainHelper.defaultService`); a class that keeps a value in defaults takes the defaults to use and never writes `UserDefaults.standard` directly.
- `MuxBotUITests`: XCUITests on an iOS simulator (`-destination 'platform=iOS Simulator,id=<iPad>' test -only-testing:MuxBotUITests`); the app launches with `-uiTesting` (in-memory store, one example bot with a blank preview). macOS UI tests need an accessibility permission, so they run on iOS.
- User-facing strings live in `MuxBot/Resources/Localizable.xcstrings` (synced from the build with `xcrun xcstringstool sync`).
